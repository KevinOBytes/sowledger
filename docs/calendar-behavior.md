# Calendar and date behavior

SOWLedger distinguishes planned work, recorded time and external availability. This note describes the intended contracts and the regression coverage; it is not a production deployment receipt.

## Dates and timezones

- Calendar, Dashboard, Activity, Analytics and Export date controls use the browser's local timezone. Calendar also displays the account timezone when it differs; changing the account preference does not silently reinterpret the browser's date inputs.
- A selected end date includes that entire local day. A daylight-saving day may span 23 or 25 hours. Browser requests send explicit UTC instants. Reports and export APIs also accept `YYYY-MM-DD`, with an inclusive UTC end day. Timer-list and schedule APIs retain their timestamp boundaries; use explicit instants rather than assuming the same date-only end behavior.
- Activity, Analytics and time-entry exports select entries by their start time. An overnight entry stays with its start day in those views. Calendar month totals split its recorded duration across the visible days; aggregate breaks are allocated proportionally because individual historical pause intervals are not stored.
- Planned hours are clipped to the selected report window. Schedule exports include any overlapping block and retain its full original timestamps.
- Task and goal due dates are calendar dates. Clearing one stores null, not January 1, 1970. Native/public task APIs and native invoice creation accept validated date-only or explicit-offset values; omission preserves an existing task date and an explicit blank/null clears it. Impossible requested dates are rejected with 400 instead of moving into the next month; invalid saved dates that prevent an edit are a 409 review conflict.
- New local-time input rejects nonexistent spring-forward times. A new or changed repeated-hour time uses the first occurrence. An unchanged saved time preserves its exact offset and seconds, including the second occurrence.
- Moving a saved plan is separate from editing its local-time input: pointer and keyboard movement preserve exact elapsed duration and start seconds/milliseconds. A repeated-hour move prefers the source offset if that target occurrence exists; otherwise it uses the first occurrence. Missing target wall times are rejected. Next slot and Duplicate preserve exact elapsed duration (including five- and 37-minute plans and fractional-minute endpoints), seek a target at or after the previous end, and retain the source start's sub-minute portion. Resize intentionally changes duration. Painted card height is never a duration measurement.
- API-key expiry is the end of the chosen local date. A deliberately blank date means no expiry.

New elapsed-time windows allocate one whole-window second budget across contiguous UTC-midnight fragments using cumulative floors, with a one-second minimum only for a positive whole window. A fragment may receive zero seconds without its geometric timestamps moving; timer stops and legacy calendar draft imports omit those zero-second fragments. The native timer reuses its original ID and schedule link for the first retained positive fragment, so its stored start may move forward; the audit retains the original start and requested stop. Aggregate pauses are deducted backward after allocation, not reconstructed as historical pause intervals. Equal-endpoint or fully paused timers close at the requested endpoint with zero seconds and a no-recorded-time audit; that is distinct from positive net time rejected by daily capacity. Historical rows and pause/resume transitions are not migrated by this allocation rule.

Recording capacity is 86,400 seconds per workspace/person and UTC **entry-start date**, across every status/source. Manual and public API entries remain unsplit, so their entire duration belongs to their start bucket; this is not exact civil-day overlap accounting. The six increasing/transferring writers (manual, edit, stop, legacy import, public create and split) serialize through one transaction-scoped owner lock and read fresh capacity after waiting. Exact binary units of the stored `real` durations prevent fractional rows disappearing in rounded totals. Stop fits the remaining whole-second capacity per bucket; the other writers reject the whole mutation. Nonincreasing corrections on historically overfull buckets remain possible, but positive transfers must fit their destinations. All associated entry, schedule and audit writes commit or roll back together; existing outgoing callbacks register only after commit. This does not serialize new workspace billing-freeze periods or guarantee exactly-once external delivery.

Pause/resume uses only the exact workspace/person/entry row lock, with the transition clock read after waiting. It never requests the capacity owner lock; stopped, missing or foreign timers are unavailable. Repeated pause/resume is a no-op in the current state. Stored pause aggregates retain fractional `real` values and reject invalid data; large historical aggregates may absorb a small addition at existing storage precision. This prevents stale whole-row transitions; it does not reconstruct missing historical pause intervals or migrate their precision.

Corrections preserve saved recorded seconds and the actual pause aggregate for equal-length moves, including retained fractional-midnight allocations. Ordinary changed-length edits keep floor-based inferred exclusions. A saved allocation above its own elapsed floor can change length only by exact whole seconds while retaining its fractional interval length; ambiguous fractional changes receive an explicit validation message. Changed durations must preserve their intended integer delta at stored precision, and splits require two positive stored children whose exact sum equals the parent. Some decimal splits (including 1 second split by 0.2 or 0.1) are refused; 0.25 and conserving whole-second splits remain supported. No timestamp is moved to absorb rounding, no negative pause is invented, and a stopped-null edit materializes inferred time only when capacity permits. This is a bounded correction policy, not reconstruction of historical pause/allocation origins or a claim that the minute-resolution editor supports arbitrary subsecond editing. Local/controlled regression checks are not hosted acceptance.

The main calendar provides Day, Week, Month and manager-only Team views, previous/next/Today navigation, Go to date, saved visible hours and a current-time marker for today's visible time range. Recorded entries link to Activity; running entries link to the timer. Background refreshes apply only their newest complete response, so a slower old response cannot hide a confirmed save or restore stale preferences.

## Plans and recorded work

A plan can start a timer or become a manual/calendar time entry once. Running, completed or already-linked work cannot be consumed again, moved, reassigned, skipped or canceled. Descriptive corrections remain available. Both directions of the time-entry link matter; editable labels and a stale planned status do not reset the history.

Imported Google events represent availability, not billable work. Their provider identity remains authoritative even if older editable labels were changed. Create a separate work block when actual client work needs to be recorded.

Native/public planned totals and revenue review share one eligible-work selection: workspace, requested project/person/date scope, overlap clipping, and exclusions for canceled, unavailable, OOO, busy and provider-identified imported availability. Recorded-entry source and approval filters do not invent a schedule-status mapping. Provider identity lookups are bounded in chunks for all-time reports. Public revenue retains its team scope; native mine/team permissions are unchanged.

Managers can load a same-workspace assignee's work types. Changing assignee visibly clears the old selection and fences late choice responses; unrelated edits preserve an existing saved action. Ordinary members can read only their own choices. Grid reassignment of a rated block requires Edit details to explicitly resolve the new assignee/rate. This does not change the separate Calendar/Activity member-visibility policy.

Repeated creation and Replace planned use one transaction. Every replacement must still match the selected version and be an editable, overlapping, unconsumed plan for the assigned member. The operation ID is a retry receipt: a committed retry returns the original IDs; changed payloads or incomplete receipts fail closed. Ordinary cancellation does not erase that receipt. Operator hard-deletion of all receipt rows is outside this guarantee.

Task list and board blocker messages describe the current view only. Native/public writes validate the full same-project relationship graph under a scoped project lock, including dependency cycles and Review/Done transitions. Board autosave retains unrelated unsaved fields; explicit task-save controls distinguish Saved, Save changes, Saving and a failed-draft retry. Attachment drafts use their independent Attach action.

Deleting an unreferenced client detaches the client link while retaining directory organizations and people. Referenced projects prevent deletion; existing orphan rows are not repaired. ORM declarations do not establish that every historical database constraint exists; catalog/data reconciliation requires a separate reviewed, backup-backed maintenance operation.

Saved invoice history accepts only the recognized duplicate-linked-ID variant with otherwise checked identity, workspace, amount, dates and explicit unknown/null audience. It preserves original IDs, multiplicity, order and saved totals, shows review guidance, and offers no proof/print/status/push controls for that record. Refresh invalidates any selected proof that becomes unavailable. Status and QuickBooks guards check persisted duplicate links after scoped locking and return 409 before side effects; missing/foreign records retain 404 and role denials remain 403. Existing direct proof, portal and approved-snapshot entitlements remain independent and unchanged: unknown audience alone is not a denial rule. Other malformed list data fails refresh without discarding the last known state. Billable-line seconds/minutes/hours are approximate presentation only; cents and proof bytes are unchanged.

## Google Calendar and reminders

Google sync serializes snapshots per workspace before reading provider state. Pagination must finish before imported availability is reconciled. Reconnecting creates a new connection generation; unknown historical or different-calendar links are left unchanged with a warning. An imported event is never treated as a SOWLedger-owned outbound event.

Canceled or skipped owned exports are removed within the requested sync window only after verifying the current connection, event identity, private ownership markers and ETag. Conditional provider writes preserve intervening changes. Deletion receipts survive a later local import failure, and restoring a plan uses a fresh deterministic event ID. If the first export response or receipt was lost, recovery probes only its deterministic current-generation ID and saves verified ownership before attempting deletion; matching titles or times are never enough. Bare 404 responses are ambiguous, not proof of deletion. Unproven events are left unchanged with a warning.

Sync reflects a bounded snapshot, not continuous background synchronization. Changes made after that snapshot need another sync. A successful local test does not confirm that a real Google account has granted access.

Reconnecting or changing Google calendar settings clears the previous successful-sync timestamp. Late results must match the current account generation and complete settings snapshot before changing connection state. A sync whose final confirmation loses that check reports a conflict rather than claiming the newly selected calendar has been synced.

Reminders skip unavailable, OOO, busy and imported availability. Notification counts distinguish provider acceptance, failures, no configured channel and deferred work. Acceptance is not proof a person received or read a message. A provider accepting a request followed by a lost response or failed local receipt can still require reconciliation; exactly-once external delivery is not guaranteed.

## QuickBooks export safety

Reconnect creates a fresh connection generation and clears the successful-sync timestamp. Refresh ownership includes the captured company/environment, full configuration and credential version. A durable refresh claim permits one rotating-token request; an unresolved claim requires explicit reconnect rather than a timed takeover. A late result cannot restore a disabled connection, overwrite a reconnection, stamp stale success/error, or start the next provider request.

Invoice eligibility locks are released before provider work. A short connection-row transaction then establishes a durable invoice claim with a stable ordinary provider request ID (at most 50 characters). No database transaction is held over provider transport. Pending claim IDs are namespaced and are not confirmations despite their required database timestamp; new confirmed storage IDs also include company/environment identity, while the public result retains the raw provider ID. A confirmed same-company/environment receipt can survive reconnect. Different-company and unbound legacy receipts require explicit review, not adoption, deletion or automatic repush.

Authorization/configuration checks happen before reserving an invoice. A reservation proven never dispatched can be abandoned; after invoice dispatch, an uncertain response or failed local receipt remains blocked pending reconciliation. A confirmed result arriving after reconnect can retain its truthful old-company receipt but cannot claim that the new company synced. Local claims and provider request IDs do not constitute an unbounded exactly-once promise. No real QuickBooks consent, financial delivery or reconciliation is established by controlled tests.

## Validation

Focused Chromium and WebKit browser suites cover the main calendar's actions, geometry, accessibility and batch saves; Dashboard plans; manual/correction dialogs; secondary date controls; and integration feedback. Main-config mobile-safari covers only its selected mobile/marketing specs, not these standalone calendar contracts. Pure interval-layout tests and browser pointer checks cover same-type and mixed overlaps, chained groups, touching boundaries and minimum-height markers. Day, Week and Team checks include desktop and phone widths, minimum card widths, aligned headers and internally scrollable dense groups. Disposable-database suites cover date persistence, schedule lifecycle, atomic batches, imported-event guards, timer contention, Google snapshot locking and reminders. The standard lint/build/full-browser/guidance checks remain required before release.

Resource planning is an assignment-and-estimate board, not a second availability calendar. Timed cards use wall-clock placement without arbitrary vertical shifts. Very short/live entries and positive-duration intervals whose local clock moves backward use a readable minimum marker; the marker's size is not a duration measurement. Clock-change descriptions include the offsets and elapsed time. Very short cards prioritize the title, with the complete time range available in the accessible description and hover text; planned work also has its existing action panel. Longer cards show the time beneath the title. The action panel retains the full status and eligible actions rather than squeezing every control into a short time slot.

Day, Week and Team pack planned and recorded cards together using their painted bounds, including expanded minimum markers. Connected overlap groups share enough columns to keep intersecting cards separate; intervals that only touch do not overlap, and disconnected cards retain full lane width. Ordering is stable by painted start, painted end and kind-qualified identity, independent of refresh ordering. Dense groups keep each card at least 80px wide by expanding only the calendar's existing internal horizontal scroll area, with matching header and body lane widths. Packed cards use compact labels while retaining complete titles and times in hover/accessibility text, full planned-work action panels, owner Activity/timer links, and existing keyboard/drag/resize controls. Vertical placement, recorded duration and timestamp semantics are unchanged.

Provider behavior is tested with controlled responses. Real OAuth consent, a hosted deployment, external notification delivery, and a physical phone's software keyboard require their own acceptance checks; local regression results do not establish those outcomes.
